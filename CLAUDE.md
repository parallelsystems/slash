# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Repository status

This is a **maintenance fork**. Upstream ([getslash/slash](https://github.com/getslash/slash)) is effectively abandoned — its last commit was January 2025 — and this fork exists so Parallel can keep the framework working. Practical consequences:

- `origin` is `parallelsystems/slash`; `upstream` is `getslash/slash`. Our default branch is `main`; upstream's is `develop`. As of this writing the only fork-only commit is `d9dcc22` (Python 3.14 support).
- Don't route fixes to upstream or assume an upstream release will land; changes ship from this fork.
- Pulling from `upstream/develop` is unlikely to bring anything. Check before assuming a rebase/merge is available.
- Several files still reference upstream and are stale rather than authoritative: the README badges point at `getslash/slash` branch `develop` (a branch this fork doesn't have, so they render broken), and `pyproject.toml` still lists upstream's author and project URLs.
- `.mergify.yml` and `bors.toml` are upstream's merge automation and are not wired up here. `.github/workflows/main.yml` is the CI that actually runs.
- Because upstream won't fix anything, dependency breakage (new Python versions, pinned deps like `dessert`/`astroid`/`pylint`) is ours to absorb — expect that to be the bulk of the work in this repo.

### How this fork is consumed

The only consumer is the `monorail` repo's testbed, which installs this fork **from GitHub, not from PyPI** — a direct reference in `testbed/requirements.txt` pinned to a specific ref:

```
slash @ git+https://github.com/parallelsystems/slash.git@<ref>
```

`testbed/compiled-requirements.txt` is `pip-compile` output (regenerated by `python3.11 make.py update`, no `--generate-hashes`) and carries the same URL verbatim — `pip-compile` passes VCS references through unchanged, so whatever ref style the source file uses appears in the lock file too. This comes from [monorail#16003](https://github.com/parallelsystems/monorail/pull/16003), which replaces the previous `slash>=1.14.0` PyPI dependency; the driver was unblocking the Python 3.14 upgrade (monorail#15924). **That PR was still open as of this writing** — until it merges, monorail is on `slash==1.15.0` from PyPI and nothing here reaches it.

> The pinning style — immutable release tag vs. commit SHA — is under active discussion and not settled. Everything below holds either way; don't assume one in new work, and check `testbed/requirements.txt` for what's actually in use.

Consequences for work in this repo:

- **Landing a commit here ships nothing.** Consumers move only when someone opens a monorail PR bumping the ref in both `testbed/requirements.txt` and `testbed/compiled-requirements.txt`. That indirection is deliberate — it puts fork changes through monorail's review process. Treat "merged to `main` here" as step one of two.
- **`main` should stay installable at all times.** Anything on it may become the pinned ref.
- **Nothing is published to PyPI**, so the `slash` distribution name in `pyproject.toml` is not what monorail resolves against; the git URL is. `hatch-vcs` still derives a version from git tags, and that version is what shows up in `pip freeze` and any SBOM, so it is worth keeping meaningful even though nothing installs *by* version today.
- **Transitive dependency bounds in `pyproject.toml` are load-bearing downstream.** They feed monorail's `pip-compile` resolution, so relaxing or tightening a bound (e.g. the `dessert>=1.6.3,<2` pin that PR #16003 carried through as `dessert` 1.4.7 → 1.6.3) can move unrelated packages in the compiled file. Expect dependency edits here to surface as a wide `compiled-requirements.txt` diff there.

### Compatibility surface: what downstream actually imports

176 modules under `monorail/testbed/` import slash. The real API contract is wider than what Slash documents — **several consumers reach into private internals**, so "no public API changed" is not sufficient evidence that a change is safe.

| What | Imported by | Notes |
| --- | --- | --- |
| `import slash` (top-level) | ~all of `projects/`, `utils/`, `drivers/` | The documented public API. Normal stability expectations. |
| `slash.plugins`: `PluginInterface`, `registers_on`, `parallel_mode` | the 5 plugins in `testbed/plugins/` | Documented, but see the silent-failure note below. |
| `slash.core.result.Result` | `plugins/test_report_plugin.py`, `utils/telemetry.py` | Private. Imported with `# type: ignore`. |
| `slash.core.metadata.Metadata` | `utils/telemetry.py` | Private. |
| `slash.exception_handling.inhibit_unhandled_exception_traceback`, `mark_exception_handled` | `testbeds/testbed.py` | Private. |
| `slash.utils.conf_utils.Cmdline`, `Doc` | `backslash` (PyPI, not ours) | See below — effectively frozen. |

Practical consequences:

- **Treat `core/result.py`, `core/metadata.py`, `exception_handling.py`, `utils/conf_utils.py` and `plugins/` as public API**, despite nothing in the code saying so. Refactoring or renaming in those modules is a breaking change for the only consumer, and neither pylint nor this repo's test suite will catch it.
- **`backslash` is a second consumer you can't patch.** `backslash==2.39.0` is pinned from PyPI and is also a getslash project, i.e. also unmaintained. It imports `slash.plugins.{PluginInterface, registers_on}` and `slash.utils.conf_utils.{Cmdline, Doc}`. Breaking those means vendoring or forking backslash too, so treat `conf_utils` as frozen.
- **Renaming a hook in `slash/hooks.py` fails silently.** `PluginManager` binds plugin methods to hooks *by matching method names*, so a renamed hook doesn't raise — the downstream plugin method simply stops being called. Grep monorail's `testbed/plugins/` for the hook name before touching `hooks.py`.
- Semver judgments for this fork should be made against monorail's actual usage above, not against upstream's notion of a public API.

## Project

Slash is a Python testing framework (a pytest alternative aimed at large integration/system test suites). The installed console script is `slash`, with subcommands `run`, `resume`, `rerun`, `list`, `list-config`, `list-plugins` (registered in `slash/frontend/main.py`).

Slash's *own* tests are written in pytest, in `tests/`. Do not confuse the two layers: code under `slash/` implements the framework; code under `tests/` uses pytest to drive it.

## Commands

Everything goes through the Makefile, which manages a `.env` virtualenv (`make env` creates it and installs `-e .[testing,doc]`). CI runs exactly `make env`, `make pylint`, `make test`, `make doc` on Python 3.11 and 3.14.

```bash
make env       # create/refresh .env virtualenv
make test      # .env/bin/pytest --cov=slash --cov-report=html tests
make pylint    # .env/bin/pylint -j 4 --rcfile=.pylintrc slash tests doc
make doc       # sphinx-build -a -W -E doc build/sphinx/html  (warnings are errors)
tox            # pylint + pytest across py311 and py314
```

Single test / subset:

```bash
.env/bin/pytest tests/test_fixture_mechanism.py
.env/bin/pytest tests/test_fixture_mechanism.py::test_name
.env/bin/pytest -k 'parallel and not tmux'
```

Notes:
- `pyproject.toml` sets `addopts = "-ra -W error::DeprecationWarning"`, so any DeprecationWarning raised during a test fails it. Deprecations inside Slash use `vintage`; tests that intentionally exercise deprecated APIs wrap them in `vintage.get_no_deprecations_context()`.
- Docs must build clean — `make doc` uses `-W`. `doc/config_doc.py` and `doc/hook_list_doc.py` generate config/hook reference pages from live code, so renaming a config key or hook can break the doc build.
- Changelog entries go in `doc/changelog.rst` using the `releases` Sphinx extension format (`* :feature:`123` ...`, `* :bug:`123 major` ...`, `-` for no issue).
- `.pylintrc` disables all refactor (`R`) checks and many style checks; max line length is 150.

## Architecture

### Run flow

`slash run` → `slash/frontend/slash_run.py` → `Application` (`slash/app.py`) → `Loader` collects runnables → `Session` is started → `run_tests()` (`slash/runner.py`) iterates and executes.

- **`Application`** (`slash/app.py`) owns the whole process lifecycle: argument parsing, loading site customization (`slash/site.py`: `~/.slash/slashrc`, project `.slashrc`, `SLASH_SETTINGS`, entry points), plugin activation, logging setup, warning capture, the `Session`, and the exit code.
- **`Loader`** (`slash/loader.py`) turns paths/addresses into runnable test objects. It imports test files through `emport` and rewrites assertions through `dessert`, applies `slashconf.py` local config (`slash/core/local_config.py`), expands parametrizations into variations, and applies filters (`-k`, `slash/utils/pattern_matching.py`).
- **`Session`** (`slash/core/session.py`) is the unit of a run: it owns the `FixtureStore`, `ScopeManager`, `SessionResults`, `CleanupManager`, warnings, logging, and the id space. Sessions are context managers (`with Session(): ...`) and are the public API for embedding Slash.
- **`run_tests()`** (`slash/runner.py`) is the actual loop: per test it sets metadata, pushes scopes, fires hooks, runs the test, collects errors into the result, and decides whether to stop.

### Global context

`slash.context` (`slash/ctx.py`) is a stack of `Context` objects; `slash.session`, `slash.test`, `slash.g` are proxies onto the top of that stack. Almost all framework code reaches the current session/test through these proxies rather than by parameter passing — this is why most of the codebase has no explicit session argument. `NullContext` is the base of the stack so attribute access outside a session returns `None` instead of exploding.

### Configuration

`slash/conf.py` declares a single `confetti` config tree (`slash.config`, accessed as `config.root.<section>.<key>`). Each leaf can carry `// Doc(...)` and `// Cmdline(...)` metadata (`slash/utils/conf_utils.py`); the command-line parser is *generated* from that metadata, so adding a CLI flag means adding a config key with a `Cmdline` annotation, not touching argparse. Tests use the `backup_config` autouse fixture plus `config_override` to mutate it safely.

### Hooks and plugins

- Hooks are `gossip` hooks in the `slash` group, all declared in `slash/hooks.py` via `_define(...)`. `slash.hooks.register` is the shorthand for registering a callback by function name.
- Plugins (`slash/plugins/`) are classes deriving from `PluginInterface`; `PluginManager` installs/activates them and binds any method whose name matches a hook to that hook automatically. Builtin plugins live in `slash/plugins/builtin/` (xunit, coverage, notifications, ci_links, signal_handling). Decorators in `slash/plugins/__init__.py` (`@parallel_mode`, `@registers_on`, `@active`, …) control how methods bind.
- `slash.ext.<name>` is a namespace-import trick (`slash/exthook.py`) mapping to third-party `slash_<name>` / `slash-<name>` packages.

### Fixtures and parametrization

`slash/core/fixtures/` implements the fixture system: `FixtureStore` holds fixture objects resolved by name and namespace (`namespace.py`), `fixture.py`/`fixture_base.py` model individual fixtures, and `parameters.py` models parametrization. Parametrization is expanded at load time into `Variation` objects (`slash/core/variation.py`, `variation_factory.py`) — one runnable test per combination, which is why test addresses carry variation ids. `ScopeManager` (`slash/core/scope_manager.py`) pushes/pops `session`/`module`/`test` scopes as the runner walks the test list and triggers fixture cleanups at the right boundary.

### Errors, results, reporting

Errors are `Error` objects (`slash/core/error.py`) added to a `Result` (`slash/core/result.py`); a test can accumulate several. `slash/exception_handling.py` centralizes the `handling_exceptions()` context manager, exception marking, and debugger entry. Reporting is pluggable via `ReporterInterface` (`slash/reporting/`), with `ConsoleReporter` as the default and `NullReporter` used when embedding.

### Parallel execution

`slash/parallel/`: the parent process runs a `ParallelManager` with an XML-RPC `Server` plus a keepalive server; workers are separate `slash run` processes (or tmux panes) that connect back, request tests from `tests_distributer.py`, and report results. Worker sessions share a session-id prefix with the parent (`Session.__init__`). Config lives under `config.root.parallel`.

### Resuming

`slash/resuming.py` persists per-session test state in a SQLite DB (SQLAlchemy) so `slash resume` / `slash rerun` can reconstruct the test list from a previous session.

## Testing conventions

`tests/conftest.py` provides the shared machinery. The two central pieces (documented in `doc/unit_testing.rst`):

- **Suite writer** (`tests/utils/suite_writer/`, fixture `suite`): builds a *virtual* test suite in memory (`suite.add_test()`, `test.when_run.raise_exception()`, `test.expect_failure()`), writes it to a temp directory, runs it via `slash_run`, and validates that what happened matches what was declared. Use it for anything about end-to-end run behavior. The `suite_test` / `last_suite_test` / `is_last_test` / `test_type` fixtures parametrize over function vs. method tests and position in the suite.
- **Suite builder** (`tests/utils/suite_builder.py`, fixture `suite_builder`): a lighter variant where you supply raw code snippets (`suite_builder.first_file.add_code(...)`) and assert on the result (`.run().assert_success(n)`).

Other conventions:
- `checkpoint` / `checkpoint1` / `checkpoint2` fixtures record that a callback fired, with ordering via `timestamp`.
- `forge` fixture (pyforge) for mocking, auto-verified on teardown.
- Autouse fixtures reset global state between tests (config backup/restore, gossip hook unregistration, user config isolation). When adding new global state to Slash, add matching cleanup here or tests will leak into each other.
- `active_slash_session` / `slash_session` / `test_loader` fixtures for tests that need a session without a full suite.
